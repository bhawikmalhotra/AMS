# Employee Attendance Management System
## Software Requirements Specification (SRS)

**Project Type:** Internship Learning Project  
**Version:** 1.1  
**Status:** Final / Updated  
**Frontend:** Next.js 16, React, JavaScript  
**UI:** Tailwind CSS, shadcn/ui  
**ORM:** Prisma 7  
**Database:** PostgreSQL 18  
**Authentication:** Auth.js / NextAuth  

## 1. Purpose

A web application for managing employee attendance. Employees manage and view their own attendance; managers can monitor employees and attendance within their own department.

The project is intentionally beginner-friendly while using realistic relational database, authentication, authorization, Prisma, PostgreSQL, and dashboard concepts.

## 2. Roles

### Employee
- Login/logout.
- View own profile and employee ID.
- Check in/out.
- View own attendance history and statistics.
- Cannot access another employee's attendance.

### Manager
A manager is a User with `MANAGER` role.
- All normal employee actions.
- View employees in their own department.
- View/filter department attendance.
- View individual employee attendance within the department.
- View department statistics and basic visualizations.
- Cannot access another department.

## 3. Functional Requirements

### Authentication
- Registered users can log in and log out.
- Protected dashboards require authentication.
- Role must be available to authorization logic.
- Passwords are never stored in plain text.
- Inactive users cannot authenticate.

### Role-Based Access Control
Supported roles:
```text
EMPLOYEE
MANAGER
```
Authorization must be enforced server-side/data-access-side.

### Employee Identity
The system stores:
- `employeeId` — human-friendly unique identifier such as `EMP0001`
- Full name
- Email
- Role
- Department
- Account status

The employee ID is separate from the internal UUID primary key.

### Departments
- Every user belongs to one department.
- A department can contain many users.
- Managers can access only users in their own department.

### Attendance
- An authenticated employee can check in once per day.
- An employee can check out only after checking in.
- An employee cannot check out twice.
- Timestamps are generated by the server.
- Duplicate attendance for the same employee/date is prevented.

Initial statuses:
```text
PRESENT
LATE
ABSENT
```

### Manager Dashboard
Supports:
- Department employee list.
- Department attendance.
- Date filtering.
- Individual employee attendance.
- Employee count.
- Present/late/absent statistics.
- Attendance percentage.
- Basic charts.

Statistics are calculated dynamically from attendance records.

## 4. Authorization Matrix

| Action | Employee | Manager |
|---|---|---|
| Login / Logout | Yes | Yes |
| Own profile / employee ID | Yes | Yes |
| Check in / Check out | Yes | Yes |
| Own attendance | Yes | Yes |
| Department employees | No | Yes |
| Department attendance | No | Yes |
| Department statistics/charts | No | Yes |
| Another department | No | No |

## 5. Business Rules

- Every attendance record belongs to exactly one User.
- Every User belongs to exactly one Department.
- At most one attendance record exists per employee/date.
- Check-out requires check-in.
- Employees access only their own attendance.
- Managers access only users in their department.
- `employeeId` is unique and human-readable.
- UUIDs remain primary keys and relationship references.
- Prefer deactivation over deleting users to preserve attendance history.

## 7. Core Database Model

```text
Department 1 ────< User 1 ────< Attendance
```

There is no separate Manager table.

```text
User.role = MANAGER
```

Each User has:
```text
id          → UUID, internal database identity
employeeId  → EMP0001, human/business identifier
```

## 8. UI Direction

Use shadcn/ui where appropriate:
Button, Input, Label, Card, Table, Badge, Dialog, Select, Calendar, Tabs, Sidebar, Dropdown Menu, Alert/Toast.

Keep the UI simple and avoid unnecessary custom design-system complexity.

## 9. Application Flow

```text
Login
  ↓
Authentication
  ↓
Role Identification
  ├── Employee → Employee Dashboard
  │               ├── Profile
  │               ├── Today's Attendance
  │               ├── Check In / Check Out
  │               ├── History
  │               └── Statistics
  │
  └── Manager → Manager Dashboard
                  ├── Department Employees
                  ├── Department Attendance
                  ├── Filters
                  ├── Statistics
                  └── Visualizations
```

## 10. Out of Scope

Payroll, leave management, salary management, biometric/face recognition, GPS attendance, shift management, multiple branches, notifications, advanced HR management, mobile application, advanced enterprise analytics, and public registration.

## 11. Acceptance Criteria

- Authentication works.
- Roles are identified correctly.
- Employees can access only their own attendance.
- Managers can access only their department.
- Check-in/check-out works.
- Duplicate daily attendance is prevented.
- Employee IDs are unique and human-friendly.
- Attendance history works.
- Manager statistics and at least one visualization work.
- Server-side authorization is enforced.
- Prisma/PostgreSQL relationships work correctly.

## 12. Development Principle

This is a learning project. Prefer simple, readable solutions and understand generated code before accepting it. Use AI/code assistants as helpers, not black boxes. Keep database design aligned with requirements and practice PostgreSQL concepts through real Prisma queries.
